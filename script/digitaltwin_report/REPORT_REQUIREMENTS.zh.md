# 报告输出规范（中文）

你必须根据输入的 JSON 数据，生成结构化、工程可执行的中文分析，不要泛泛而谈。

## 固定结构
1. 总评
- 三句话, 描述整体情况, 给出水厂运行是否稳定, 得出结论，结论为：`稳定` / `关注` / `风险` 之一并给出原因。

2. 当前运行状态（基于 sim_recorder）
- 只聚焦 `CSTR*_SNOx` 与 `EFF*` 指标。
- 指出最关键的 1-3 个运行现象。

3. 预测简述（基于 sim_predict）
- 仅描述均值趋势，不展开冗长解释。

4. 预警原因与工艺诊断
- 对每条预警，说明：
- 预警等级（一般/重要/紧急）
- 可能原因（工艺+运行角度）
- 工艺诊断（可操作）

5. 操作建议
- 最多 3 条，按优先级排序（P1/P2/P3）。
- 每条建议必须具体到“检查/调整什么”。

6. AI加碳策略专项分析（必选）
- 必须单独输出该小节，不得省略。
- 重点不是三表如何生成，而是“这三表对当前加碳策略给出了什么建议、当下状态如何”。
- 必须结合 `snox_target / front_snox / snox_gap` 判断当前策略是偏紧/偏松/基本匹配。
- 必须说明下一步建议动作（增碳/降碳/保持）及理由。

## 约束
- 不要编造数据库不存在的事实。
- 如 `sim_recorder` 或 `sim_predict` 数据不足/为 N/A，不得跳过分析：
- 必须说明可能原因（如当天数据为空、字段不匹配、采集延迟）
- 必须转而基于 `carbon_opt_task / carbon_opt_schedule / carbon_opt_front` 给出运行判断
- 输出尽量简洁，优先实操价值。
- 对所有 `N/A / NaN / 空值`，禁止只做“数据缺失”复述，必须进行诊断推理：
- 先判断缺失类型：采集缺失 / 同步缺失 / 字段映射问题 / 当日未出实验室值 / 业务场景本就低频。
- 再给出“可验证证据”与“下一步动作”：应检查哪张表、哪个字段、哪个链路（采集->同步->S3->报告）。
- 若关键指标缺失，必须给“替代判断路径”：使用同类指标、历史最近值、三表策略链、上下游关联指标进行保守结论。
- 当无法确认唯一原因时，必须输出“最可能原因Top2-3 + 排查优先级（P1/P2/P3）”，不得直接下确定性结论。

## AI加碳策略专项强化规则（必须执行）
- 不得仅凭 `task_count` 判断策略是否频繁，因为任务可能按小时固定触发。
- 必须优先基于“加碳值调整频率/幅度”（如 adjust_ratio / adjust_span）判断是否真正频繁调节。
- 若出现“低频调整 + 长时间高位加碳”，必须明确提示以下风险之一：
- 目标值/约束偏紧导致持续高投加；
- 预测或负荷基线偏高导致保守高投加；
- 反馈链路钝化导致高位设定长期不回落。
- 上述场景下必须给出可执行动作：小步降碳试探（3%-5%）、观察2-3个周期的 NOX 与 EFF 变化、复核目标边界与模型输入。

## 工程约束（必须遵守）
- English 切换是翻译行为，不得触发第二次完整报告推理。
- 仅在“切换 Provider”或“点击更新AI分析”时允许重新调用 LLM。
- 若未检测到明确缺失事实，不得输出“运行数据缺失/大面积缺失”。
- Sensor Validate 视图遵循 Dash 规则：漂移由 clean_data 分段着色表达，非必要不额外画 drift_prob/drift_degree 线。
- 异常判定规则提示采用“小 i 图标 + 补充说明”形式，放在对应异常语句旁，不放在大标题后。
- 分析渲染必须支持真实 Markdown 层级（标题、编号列表、无序列表、粗体/斜体），不得直接暴露原始 `**`、`*` 标记。
- 修改后必须执行最小验证：`py_compile` + `/api/report` + `/api/diagnostics` 冒烟检查。
